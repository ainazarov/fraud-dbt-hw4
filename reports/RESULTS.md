# Результаты проверки и оптимизации

Полный запуск 5 октября 2026 года подтвердил правильность загрузки обоих CSV через Kafka в ClickHouse и совпадение трёх SQL-запросов с независимым эталоном Python. Предагрегация уменьшила медиану серверного времени с **51 до 1 мс для train** и с **21 до 1 мс для test**. Оптимизированная таблица исходных строк заняла на **51,46% меньше** сжатых данных; ускорения запроса по этой таблице в данном эксперименте не получено.

Эталон читает CSV через `csv.DictReader`, сравнивает суммы через `Decimal` и не использует функции producer. Проверены все региональные максимумы и точные количества строк; дополнительно по 7 исходных строк в каждой таблице проверены все поля и идентификаторы. При равной сумме выбирается лексикографически наибольшая категория, затем наибольший `transaction_id`.

## Измерение запроса

Стенд: один ClickHouse **25.3.6.56** в Docker под удалённым WSL2, Linux `6.6.114.1-microsoft-standard-WSL2`; AMD Ryzen 7 7800X3D, 8 ядер / 16 логических CPU, около 15,2 GiB доступной системе памяти. Docker Engine **29.8.1**, Compose **5.5.1**, Python **3.11.11**. Подробности: [CPU](lscpu.txt), [Docker](docker-version.txt), [метаданные измерения](benchmark_train.json).

Для каждого запроса выполнены один прогрев и **15 измерений**, `max_threads=2`, `use_query_cache=0`. Порядок трёх вариантов перемешивается в каждом раунде с фиксированным seed. Кэши ОС не сбрасывались: это последовательный тест с прогретым кэшем. Перед каждым набором измерений `--compact` выполнил `OPTIMIZE TABLE ... FINAL` только для трёх таблиц проекта. Серверные показатели получены из `system.query_log`: `QueryFinish`, `is_initial_query=1`, уникальный `query_id`; клиентское время HTTP измерено отдельно.

| Данные | Вариант | Медиана сервера, мс | Диапазон сервера, мс | Медиана HTTP, мс | Медиана `read_rows` | Медиана `read_bytes` |
|---|---|---:|---:|---:|---:|---:|
| train | Baseline, обычные строки / LZ4 | 51 | 50–55 | 52,454 | 1 048 605 | 102 128 964 |
| train | Raw, сортировка / LowCardinality / ZSTD | 52 | 51–73 | 53,972 | 835 655 | 70 202 751 |
| train | Aggregate, `argMaxMerge` | 1 | 1–1 | 2,705 | 109 | 15 698 |
| test | Baseline | 21 | 20–22 | 22,121 | 1 048 605 | 43 654 036 |
| test | Raw | 21 | 21–23 | 22,754 | 335 830 | 24 248 438 |
| test | Aggregate | 1 | 1–1 | 2,675 | 109 | 15 698 |

Серверное `query_duration_ms` имеет разрешение 1 мс, поэтому отношения 51× и 21× следует считать приблизительными. По клиентской медиане с HTTP предагрегация быстрее baseline примерно в **19,39×** и **8,27×** соответственно. Raw читает меньше строк и байт, но по времени train немного медленнее, а test совпадает в пределах миллисекундного разрешения. Разброс отдельных запусков, особенно raw/train до 73 мс, отражён в таблице.

Baseline читает все **1 048 605** физических строк: 786 431 train + 262 144 test + 24 demo + 6 строк потокового теста с повторной отправкой. В маленькой `state_max` всего **109** состояний для всех наборов, включая 51 train и 51 test. Запрос читает одну общую гранулу из 109 строк, затем возвращает 51 строку выбранного набора. Это подтверждают планы: [aggregate/train](explain_aggregate_train.txt), [aggregate/test](explain_aggregate_test.txt). Первичный индекс raw отбирает гранулы по `dataset`; помесячное разбиение само по себе здесь не исключает месяцы, поскольку фильтра по времени нет: [raw/train](explain_raw_train.txt), [raw/test](explain_raw_test.txt).

Все наблюдения, включая память: [сводка train](benchmark_train.json), [сводка test](benchmark_test.json); исходные 45 измерений на набор: [train](benchmark_samples_train.csv), [test](benchmark_samples_test.csv).

## Объём хранения и цена оптимизации

Снимок `system.parts` из измерения train; только активные части, **все загруженные наборы вместе**:

| Таблица | Физических строк | `data_compressed_bytes` | `bytes_on_disk` |
|---|---:|---:|---:|
| `transactions_baseline` | 1 048 605 | 150 195 239 | 150 207 553 |
| `transactions` | 1 048 605 | 72 906 868 | 72 959 534 |
| `state_max` | 109 | 5 766 | 5 884 |

Сжатые данные raw занимают в **2,06 раза меньше**, чем baseline: 69,53 MiB против 143,24 MiB. Предагрегация добавляет 5 766 байт сжатых данных в этом снимке. Baseline сохранён для контрольного сравнения и сам занимает дополнительное место. Снимок test сделан отдельно после ещё одного `OPTIMIZE FINAL`: raw занимает 72 908 786 байт, на 1 918 байт больше; число строк и результаты не изменились. Это различие физических снимков, а не размер отдельного test.

Главный выигрыш времени даёт хранение готовых состояний максимума. Материализованное представление переносит часть работы на вставку; ZSTD и поддержка дополнительных таблиц также требуют ресурсов при загрузке. Стоимость вставки отдельно не сравнивалась. Полученные времена относятся к конкретному стенду, объёму и прогретому кэшу; они не характеризуют холодный запуск или параллельную производственную нагрузку.

## Воспроизведение

Подготовка данных и запуск описаны в [README](../README.md), полный сценарий — [scripts/full_run.sh](../scripts/full_run.sh). Для повторного полного импорта нужен новый Compose-проект с чистыми томами либо новые имена наборов; повторная отправка в существующие train/test добавит физические строки. Контрольный стенд перед полным запуском также содержал demo и потоковый тест, поэтому при запуске только full_run количество прочитанных baseline строк будет меньше на 30.

После успешной загрузки проверку сохранности можно повторить из корня проекта; повторная публикация в Kafka не нужна:

```bash
docker compose restart clickhouse
docker compose up -d --wait --wait-timeout 240 clickhouse
docker compose --profile tools run --rm verify /data/train.csv --dataset train --output-dir /results/restart
docker compose --profile tools run --rm verify /data/test.csv --dataset test --output-dir /results/restart
```

В сохранённом запуске обе проверки после перезапуска завершились со статусом `passed`, с прежними точными количествами строк и теми же максимумами.
